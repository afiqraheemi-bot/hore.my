## 1. Purpose

This document specifies the Proof of Accuracy required by the Master Context §10 and §19 before a full AI workflow may reach real ledger posting. It defines the controlled golden dataset, exact deterministic comparisons, certification evidence, and pass/fail conditions.

This Draft does not certify the current implementation. Until it is reviewed and activated, Proof of Accuracy remains **not passed** and full AI remains blocked from real posting.

## 2. Scope

### 2.1 In scope

- One version-controlled golden dataset covering, in a connected scenario, a receipt, bank statement, business transactions, invoice, posted journals, Trial Balance, and supported financial reports.
- Exact validation of Money, journal balance, report totals, source/evidence traceability, duplicate prevention, tenant isolation, and repeatability.
- A release-candidate certification record identifying the dataset, source revision, runtime, database, results, and approvals.
- The boundary between a manually approved source interpretation and Accounting Core's deterministic processing.

### 2.2 Out of scope

- OCR accuracy, model/provider selection, prompts, confidence thresholds, or AI evaluation.
- MyInvois, Cash Flow, Reconciliation Report, PDF/XLSX export, quotations, or Compliance Pack behavior not yet governed by an Active specification.
- Backup/restore, load, availability, monitoring, incident-response, security, or production-readiness certification. Proof of Accuracy is necessary but not sufficient for release.
- New accounting rules. Expected results may only instantiate behavior already defined by Active AETS documents.

## 3. Authority and activation

This document implements Master Context §10, §18, and §19 and ADR-0004/ADR-0005, subordinate to [AETS-000 §3](AETS-000.md#3-authority-hierarchy). Activation requires the review mandated by [AETS-000 §8.2](AETS-000.md#82-ownership-and-review), including an Accounting Domain Reviewer. A dataset cannot become an approved accounting oracle merely because its tests pass or an implementer authored it.

## 4. Definitions

- **Golden Dataset:** A versioned, immutable-for-that-version collection of source artifacts, approved canonical facts, command inputs, and expected accounting outputs used as an external oracle. Expected results are reviewed values, not values generated by the implementation under test.
- **Proof of Accuracy:** A repeatable certification run showing that a named source revision, against one approved Golden Dataset version, produces every required deterministic result exactly and violates none of the safety checks.
- **Canonical source facts:** Human-reviewed structured facts represented by a source artifact. They are test input, not an AI prediction.
- **Certification record:** The immutable report of one run, including identity, environment, results, exceptions, and approvals.

These definitions are local to this Draft. If activated, their canonical wording must also be added to AETS-001 as required by AETS-001 §4.

## 5. Golden Dataset contract

### 5.1 Version and integrity

Each dataset version MUST have a stable identifier and a manifest containing a cryptographic digest for every source and expected-output artifact. An approved version is never edited in place. Any change creates a new version, records its reason, and repeats approval and certification.

The manifest MUST distinguish original sources, manually approved canonical facts, deterministic command inputs, expected Journals/audit/evidence links, and expected reports. Expected outputs MUST NOT be captured from the implementation under test and then treated as approval evidence.

### 5.2 Required connected coverage

| Required artifact | Minimum proof |
| --- | --- |
| Receipt | Original hashed artifact, approved canonical facts, Source Fingerprint, Evidence Reference, confirmed transaction, and resulting Journal. Receipt interpretation may be an approved oracle while OCR/AI is absent. |
| Bank statement | Original hashed supported file, exact normalized rows, duplicate-file replay, overlapping-row deduplication, and closing balance used by reconciliation. |
| Transactions | At least one evidence-backed Expense and one Income or Invoice-originated revenue flow through real services and the generic Posting Command pipeline. |
| Invoice | Issued Invoice with exact line total, receivable/revenue Journal, stable number, and point-in-time Aging result. |
| Journals | Expected identity/source, Financial Date, Account, Direction, Money, state, evidence links, and Audit Events all match exactly; every Journal balances and is Posted. |
| Trial Balance | Account Debit/Credit totals and grand totals match exactly, and total Debit equals total Credit. |
| Reports | Every report supported by Active AETS-009 for the scenario reconciles to the same Journals; no separately stored report total is an oracle. |

Tenant-isolation data MUST include a second Tenant with deliberately colliding visible dates, descriptions, amounts, and document names, so isolation is demonstrated rather than assumed.

### 5.3 Receipt boundary before AI

The first dataset may pair a real hashed receipt with human-approved canonical facts and submit only the resulting confirmed deterministic command. This proves the receipt-backed accounting path and evidence lineage; it MUST NOT be reported as proof of OCR or AI accuracy. Later Document Processing/AI regression gates supplement rather than replace this Proof of Accuracy.

## 6. Execution requirements

A certification run MUST:

1. start from a clean database created by production migrations;
2. use a real supported PostgreSQL instance, never SQLite or mocked persistence;
3. use real services and the ordinary Posting Command pipeline, never direct inserts of expected Journals or report totals;
4. use controlled clocks/identities where exact time or identity is asserted;
5. compare minor units, Currency, dates, Directions, identifiers, links, states, and counts exactly;
6. prove replays and duplicate sources create no extra authoritative row or economic effect;
7. run from at least two independent clean states with identical deterministic outputs, excluding declared operational timestamps;
8. treat skipped tests as failure;
9. retain machine-readable results and a human-readable certification record; and
10. fail closed for any missing artifact, digest, expected result, test, or approval.

## 7. Acceptance criteria

There is no tolerance band for deterministic financial output.

| ID | Acceptance criterion |
| --- | --- |
| POA-001 | Every manifest digest verifies; dataset version/approval and all mandatory artifacts exist. |
| POA-002 | Every §5.2 category exists in one stable source/evidence/transaction/Journal/report chain. |
| POA-003 | Every Money value equals the approved Currency/minor-units exactly; binary floating point is absent. |
| POA-004 | Every Posted Journal has at least two lines and exact Debit equals Credit; Draft Journals affect no report. |
| POA-005 | Trial Balance, Profit & Loss, Balance Sheet, General Ledger, Evidence Index, and Aging outputs governed by Active AETS-009 reconcile exactly to the same ledger. |
| POA-006 | Required replay/deduplication cases create no duplicate import, transaction, Journal, Audit Event, evidence link, Invoice, or economic effect. |
| POA-007 | A second Tenant with colliding visible values cannot read, alter, match, reconcile, or report the first Tenant's records. |
| POA-008 | Receipt/Invoice evidence and material Audit Events are complete and traceable; no evidence is fabricated. |
| POA-009 | Independent clean-state reruns produce identical deterministic outputs. |
| POA-010 | Real-PostgreSQL tests finish with zero failures, errors, skips, incomplete, or risky tests. |
| POA-011 | Certification records dataset/digests, Git revision, runtimes, commands, counts, deviations, and approvals. |
| POA-012 | Any failed or missing criterion fails the whole gate; partial coverage is never called Proof of Accuracy passed. |

## 8. Certification record

Every record MUST include a unique ID and UTC time; Git hash and tree status; dataset version/manifest digest; PHP, Laravel, PostgreSQL and test-runner versions; exact commands/status; pass/fail/error/skip/incomplete/risky counts; every `POA-NNN` result; deviations; CTO review; and Accounting Domain Reviewer approval. A deviation means failed, not conditionally passed. Founder approval is additionally required if a dataset revision changes product scope, risk, cost, or user-visible treatment.

## 9. Failure and change policy

- A failure is a release blocker and is never waived by regenerating expectations from current behavior.
- A legitimate policy correction creates a reviewed dataset version and, where applicable, versioned AETS/ADR changes first.
- A code defect is fixed in code; the approved oracle stays unchanged.
- An ambiguous/corrupt source is replaced only in a new version with reason and approval.

## 10. Required test specification

[ATS-012](tests/ATS-012-Proof-of-Accuracy-Test-Specification.md) defines the required tests. Neither it nor test code may mark this Draft certified.

As of 2026-09-16, the certification harness's own domain-agnostic mechanism — Golden Dataset manifest parsing and digest-integrity verification, and the fail-closed `CertificationRecord` aggregation gate implementing `POA-012` — is implemented and proven with synthetic, explicitly-not-a-real-oracle fixtures (see [ATS-012 §5.1](tests/ATS-012-Proof-of-Accuracy-Test-Specification.md#51-certification-harness-infrastructure-only--no-dataset-no-certification)). This is infrastructure only: it does not create, approve, or imply a Golden Dataset, run any certification scenario, or move this Draft any closer to Active. Every §11 deferred decision remains exactly as deferred.
