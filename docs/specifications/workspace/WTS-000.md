## 1. Purpose

The Workspace & Task Specification (WTS) series is the technical specification series for hore.my's Workspace and Task module — the module that owns the "evidence/instruction → Task → Interpretation → Proposal → Human review → Approved Command → Completion" flow described in [`HORE_MY_MASTER_CONTEXT.md`](../../product/reference/HORE_MY_MASTER_CONTEXT.md) §4–§5 and named Module 3 in §8.

This document, WTS-000, is the foundation of that series. It exists to state the series' purpose, scope, and authority; record the product and AI-boundary philosophy every later WTS document must remain consistent with; define how WTS documents are governed, reviewed, versioned, and numbered; and lay out the series' planned structure.

WTS-000 does not itself define the Task/Proposal state machine, schema, or invariants — that is [WTS-001](WTS-001-Task-Proposal-State-Model.md).

## 2. Scope

### 2.1 In scope for the WTS series

- Task and Proposal entity design, state machine, and lifecycle invariants.
- The Proposal-to-Accounting-Command relationship: what a Proposal must contain for its approval to become a valid Accounting Core Command, and what Workspace/Task validates before submitting one.
- Human Confirmation semantics — what "approval" must mean and record.
- Task-lifecycle audit/transition schema (deliberately separate from [AETS-010](../accounting/AETS-010-Audit-Trail-Evidence-Linkage.md)'s Journal-scoped audit trail, per [ADR-0009](../../adr/0009-workspace-task-module-boundary.md)).
- Approval-time idempotency and concurrency contract.
- The Task-side contract for consuming evidence references (not evidence storage/retention itself).

### 2.2 Out of scope for the WTS series

- Accounting invariants of any kind — those remain [AETS-002](../accounting/AETS-002-Accounting-Invariants.md)'s exclusive domain; WTS never redefines, weakens, or duplicates them.
- AI/OCR provider selection, model choice, prompt design, and routing — owned by AI Orchestration under [ADR-0005](../../adr/0005-ai-provider-abstraction.md). WTS defines only what a Proposal must structurally contain, not how one is produced.
- Document Processing's evidence storage, retention, versioning, and classification design — its own future specification.
- UI visual design — a product/UX artifact, not a technical specification.
- Everything listed as out of MVP scope in [`HORE_MY_MASTER_CONTEXT.md`](../../product/reference/HORE_MY_MASTER_CONTEXT.md) §9.

## 3. Authority hierarchy

WTS is a technical specification series, not a source of product or architectural authority, exactly as [AETS-000](../accounting/AETS-000.md) §3 establishes for AETS. The same precedence governs both series:

1. Latest Founder instruction
2. [`HORE_MY_PROJECT_INSTRUCTIONS.txt`](../../product/reference/HORE_MY_PROJECT_INSTRUCTIONS.txt)
3. [`HORE_MY_MASTER_CONTEXT.md`](../../product/reference/HORE_MY_MASTER_CONTEXT.md)
4. System Requirements Specification, as corrected by [`SRS_OVERRIDES.md`](../../product/reference/SRS_OVERRIDES.md)
5. Detailed Project Proposal
6. Accepted Architecture Decision Records (`docs/adr/`)
7. AETS and WTS documents, as siblings — neither series may weaken, override, or contradict the other or any higher source. Where WTS references an accounting concept (a Command, a Journal, a closed Period), the corresponding AETS document is authoritative for that concept's own behavior; WTS may only describe how Workspace/Task calls into it, never redefine it.

If a conflict between a WTS document and a higher-precedence source is discovered, it is a defect in the WTS document and must be corrected via the versioning rule in §8.

## 4. Product philosophy

Directly inherited from [`HORE_MY_MASTER_CONTEXT.md`](../../product/reference/HORE_MY_MASTER_CONTEXT.md) §4–§5 and restated here because every WTS document must design to it:

- **Action-first, not conversation-first.** A Task exists because the user supplied evidence or an instruction, not because they are chatting. Every Task has an objective, a status, an available action, and a terminal result.
- **Automate the obvious; ask only about material uncertainty.** A Task should not manufacture busywork by asking about things that can be determined confidently, and must not hide uncertainty when it cannot.
- **Nothing posts without confirmation.** A Proposal is not a Command. No Task reaches Accounting Core until an authenticated human actor has explicitly approved it — see §5.
- **Every Task is traceable.** A completed Task's full story (its evidence, its Proposal, who approved it and when, and the resulting Journal) must be reconstructable, mirroring the ledger-side traceability [AETS-000](../accounting/AETS-000.md) §4 already requires of Accounting Core.

## 5. AI boundary

Restated from [ADR-0005](../../adr/0005-ai-provider-abstraction.md) as it applies specifically to Task/Proposal, because every WTS document must design to it:

- AI may create or update a Proposal only while that Proposal's Task is in a `NeedsInformation`-or-earlier or `NeedsReview`-or-earlier state (see [WTS-001](WTS-001-Task-Proposal-State-Model.md) §3–§4 for exact adjacency).
- Only an authenticated human actor's explicit action may perform the `NeedsReview` → `Approved` transition. No system, scheduled process, or AI producer may perform it automatically, regardless of confidence score.
- Accounting Core never receives an unapproved Proposal. AI has no code path, credential, or database permission capable of reaching a Command or a Journal — this is a structural fact of the module boundary ([ADR-0009](../../adr/0009-workspace-task-module-boundary.md)), not a policy AI is merely instructed to follow.
- Every AI-produced Proposal must carry the provider/model identifier, model version, prompt/schema version, confidence score, and the evidence it relied on — the full contract for this is deferred to a future WTS document (§9) written once AI Orchestration exists, and must not weaken this section.

## 6. Design principles

Applying Engineering Blueprint §2 and mirroring [AETS-000](../accounting/AETS-000.md) §7's pattern, specifically for Workspace/Task:

- **Explicit boundaries.** Task/Proposal business rules live in the Workspace/Task domain, not in controllers or a UI layer, and never inside Accounting Core.
- **Deterministic before probabilistic.** The Proposal-to-Command translation and Accounting Core's validation are designed and specified first; AI's contribution is a validated input to a Proposal, never a shortcut around human confirmation or Accounting Core validation.
- **Idempotent by default.** The Approved→Executing transition's idempotency mechanism is a required part of any WTS document that touches it, not an afterthought.
- **Two audit trails, one story.** Task-lifecycle audit records and Accounting Core's Journal-posting audit records are structurally separate (per [ADR-0009](../../adr/0009-workspace-task-module-boundary.md)) but must be specified together with how they correlate, so a human operator can reconstruct one coherent story.
- **Small, reversible change.** A later WTS document supersedes an earlier one rather than silently rewriting it, exactly as [AETS-000](../accounting/AETS-000.md) §9 already establishes for AETS.
- **Tenant isolation as a first-class constraint.** Every Task/Proposal schema and query pattern must be evaluated for cross-tenant leakage risk explicitly.
- **No invented complexity.** Task/Proposal has no financial invariant of its own. A WTS document must not manufacture accounting-grade ceremony where a simpler, still-disciplined design suffices — but must not skip the specific, named requirements the Founder's own directive and [ADR-0009](../../adr/0009-workspace-task-module-boundary.md) already impose (transition audit fields, approval idempotency, closed-period re-check).

## 7. Document governance

### 7.1 What a WTS document is

A WTS document is a detailed technical specification for one bounded concern within Workspace/Task's scope (§2.1). It is written for implementers: precise enough to build from, testable, and traceable to the ADRs and product references that authorize it.

### 7.2 Ownership and review

WTS documents are owned by Workspace and Task, under the repository's [`CODEOWNERS`](../../../CODEOWNERS) policy. A new or materially revised WTS document requires review from the CTO / Technical Partner. Founder / Product Owner review is required where a document changes scope, cost, risk, or user experience, per [`HORE_MY_PROJECT_INSTRUCTIONS.txt`](../../product/reference/HORE_MY_PROJECT_INSTRUCTIONS.txt).

### 7.3 Lifecycle

Each WTS document (including this one) carries a `Status` field: `Draft` (under active writing or review; not yet governing implementation), `Active` (reviewed and governs current implementation), `Superseded` (replaced by a later WTS document, kept for historical traceability), or `Deprecated` (no longer applicable, without a replacement).

### 7.4 Relationship to ADRs and AETS, and conflict handling

WTS documents must cite the ADR(s) they implement in a `Related` field. If implementing a WTS document would require a decision an existing ADR does not cover and that meets the Engineering Blueprint's ADR criteria, the ADR is written and accepted first. WTS content is never used to justify skipping a required ADR, and never used to redefine an AETS invariant — see §3.

### 7.5 Location and file naming

WTS documents live in `docs/specifications/workspace/`, named `WTS-NNN.md` with a zero-padded, sequential, never-reused number, plus this directory's `README.md` as the series index.

## 8. Versioning

Each WTS document carries its own `Version` field using `MAJOR.MINOR.PATCH`, with the same meaning [AETS-000](../accounting/AETS-000.md) §9.1 assigns: **MAJOR** changes a workflow outcome, invariant, or contract the document describes; **MINOR** clarifies or adds detail without changing previously specified behavior; **PATCH** is an editorial fix. A MAJOR change on an `Active` document increments the version and records a changelog note at the bottom of the document, mirroring the pattern already established across this repository's ADRs and AETS documents.

The WTS series itself is not independently versioned; its state at any time is the set of documents currently `Active`, indexed in [`README.md`](README.md).
